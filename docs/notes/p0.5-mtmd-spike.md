# P0.5 spike — does `llama-cpp-2` expose mtmd?

**Verdict: YES — but only behind the `mtmd` cargo feature. No separate
`runa-engine/sys-mtmd` bindgen crate is needed.**

## Question (plan P0.5)

> Does the pinned `llama-cpp-2` expose mtmd (`mtmd_init_from_file`,
> `mtmd_tokenize`, `mtmd_helper_eval_chunks`)? If not, add
> `runa-engine/sys-mtmd` (bindgen over `mtmd.h`, same llama.cpp checkout).

## Answer

`llama-cpp-2` exposes libmtmd through its `mtmd` feature flag, which
forwards to `llama-cpp-sys-2/mtmd`. It is **not** in the default build,
which is why the docs.rs default-build page shows no `mtmd_*` symbols.

All three functions the question names are present:

| Function | Header |
|----------|--------|
| `mtmd_init_from_file` | `tools/mtmd/mtmd.h` |
| `mtmd_tokenize` | `tools/mtmd/mtmd.h` |
| `mtmd_helper_eval_chunks` | `tools/mtmd/mtmd-helper.h` |

## Mechanics (from `llama-cpp-sys-2` build.rs)

When the `mtmd` feature is on, the sys crate:

1. Adds bindgen generation over `tools/mtmd/wrapper_mtmd.h` with
   `.allowlist_function("mtmd_.*").allowlist_type("mtmd_.*")`.
2. Compiles `tools/mtmd/**/*.cpp` (excluding `mtmd-cli.cpp` and
   `deprecation-warning.cpp`) into a static `libmtmd` via `cc::Build`
   and links it (so the `mtmd_*` symbols resolve at link time).

## Consequence for runa-engine

Enable the feature explicitly in `crates/runa-engine/Cargo.toml`:

```toml
llama-cpp-2 = { version = "=0.1.156", features = ["metal", "mtmd"] }   # macOS
llama-cpp-2 = { version = "=0.1.156", features = ["mtmd"] }            # others
```

No `sys-mtmd` crate, no second bindgen pass, no separate llama.cpp
checkout. plan.md D2 already lists `mtmd` among the `llama-cpp-2`
features (cuda, metal, vulkan, openmp, native, mtmd).

## Caveats

- `mtmd.h` opens with: "This API is experimental and subject to many
  BREAKING CHANGES." The wrapper in P2/P4 must pin against the exact
  `llama-cpp-2` version and be re-verified on each monthly bump (D16).
- Video input is helper-level only (`mtmd-helper.h`) and requires a
  system ffmpeg/ffprobe on PATH for webp/video decode; image (stb_image)
  and audio (miniaudio) decode are built in.
- `mtmd_get_memory_usage` (needed by P1/P4.8 mmproj fit math) is a C++
  `std::map`-returning function marked "unstable, used internally by
  fit_params" — bindgen will not expose it over the C ABI. mmproj memory
  accounting should instead come from the GGUF header (P1.3) and a
  calibrated compute-buffer estimate, matching the `runa-fit` plan.

## Validation note

The P0.5 "loads an mmproj and answers a question" end-to-end check is
deferred to P4.3/P4.6, where the full media pipeline lands; this spike
answers the API-existence question that gates whether `sys-mtmd` is
needed. It is not.
