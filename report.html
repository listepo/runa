Rust-раннер с честным «влезет ли», мышлением и аудио/видео

Как написать на Rust программу, которая запускает модели с глубоким мышлением, аудио и видео в трёх режимах (CPU, GPU, CPU + GPU), с конфигами и командной строкой, умеет ходить в OpenAI и Anthropic и заранее говорит, запустится ли модель на этой машине и как быстро. Рабочее имя проекта — runa.

Макет вывода runa fit: вердикт печатается до скачивания модели и до первого токена. Числа иллюстративные, формулы — в разделе «Fit-чекер».

Не новый движок, а умный слой

Все 20+ раннеров, которыми реально пользуются, — оболочки над llama.cpp/ggml. Горячие C/asm-ядра под каждую платформу там уже есть и обновляются ~50 сборок в неделю. Свои ядра — только там, где профиль показывает пробел, и только при выигрыше ≥ 5 %.

Ниша — замкнутый цикл fit

Оценка «влезет ли» есть у llama.cpp, LM Studio, gguf-parser-go, llmfit, но никто не соединяет прогноз до скачивания, запуск тем же планировщиком, замер и поправку прогноза. Ollama при этом молча падает на CPU (issue #14258 открыт).

Одна ручка мышления на всё

Бюджет и уровень усилий одинаково применяются к Qwen3, gpt-oss, DeepSeek локально и к OpenAI (reasoning.effort) и Anthropic (thinking: adaptive + output_config.effort). Ни у одного аналога этого нет.

Что делает runa

runa fitЗаголовок GGUF по HTTP range-запросу, проба железа, вердикт FITS gpu / hybrid / cpu / NO, память по устройствам, прогноз скорости с интервалом, что изменить.
--mode cpu|gpu|hybrid|autoОдин планировщик размещения: слои на GPU, эксперты MoE на CPU, квантованный KV-кэш.
--think / --think-budget / --effortПринудительный бюджет рассуждений локально, маппинг на OpenAI и Anthropic; рассуждения и ответ — раздельные потоки.
--audio / --videoДекодирование на Rust, кодировщики на C (mtmd, whisper.cpp); маршруты native / ASR / cloud с учётом того, что облака не принимают видео.
on_unfit = error|cpu|cloud:…Никаких тихих решений: политика задаётся явно, вердикт печатается всегда, коды выхода 0/1/2.

Подтверждённые боли аналогов
  • Ollama: модель «запустилась», но в 10 раз медленнее — тихий откат на CPU без предупреждения (issue #14258, открыт).
  • llama.cpp: --ctx-checkpoints копил RAM, чинилось в 2026 (issue #24055, PR #22929). Вывод: считать всё, что аллоцирует движок, и калибровать по конкретной версии.
  • llama.cpp: учёт mmproj в --fit документацией не подтверждён; VLM после «подгонки» может не влезть.
  • Ollama MLX: с 0.19 (март 2026) только preview, ≥ 32 ГБ и одна модель.
Что не делает никто
  • Замкнутый цикл fit: прогноз до скачивания → запуск тем же планировщиком → замер → поправка коэффициента для пары (устройство, квант).
  • Одна ручка мышления для локальных и облачных моделей, с учётом бюджета рассуждений во времени ответа.
  • Аудио + видео + облако с честной таблицей маршрутов: Anthropic не берёт аудио — ASR → текст; видео не берёт никто — кадры + транскрипт.
  • Нет тихих решений: on_unfit явно, вердикт всегда, коды выхода 0/1/2.

Правило D1. ggml уже содержит SME (через KleidiAI) и AMX-пути. «Горячие части на C/asm» означает: собирать ggml с правильными флагами под платформу и добавлять свои ядра только там, где профилировщик показывает пробел — семплирование по словарю 150k токенов, препроцессинг изображений, аудио-фронтенд, и как исследовательская задача — квантованный mat-vec на SME2/AMX. Каждое ядро: скалярный эталон, fuzz-тест эквивалентности, criterion-бенч, runtime-диспетчер. Гейт слияния — ≥ 5 % сквозного tok/s или ≥ 2× на операции.

Три режима

CPU, GPU, CPU + GPU — это один планировщик размещения

Ручка llama.cppЧто делаетВ runa
-ngl N / --gpu-layers autoсколько слоёв на GPUgpu = все, cpu = 0, hybrid = N от планировщика
-ot <regex>=CPU / --n-cpu-moe Nтензоры экспертов MoE на CPUhybrid для MoE: внимание и общие слои на GPU, эксперты в RAM
--device, --tensor-splitсписок устройств, долиmulti-GPU (P2.9)
--cache-type-k/v q8_0квантованный KV-кэш (нужен flash attention)--kv q8_0 в fit и в запуске
--fit, --fit-marginавто-подгонка при загрузке«точный режим» fit-чекера для локального файла

Гибрид важен именно для MoE: у Qwen3-30B-A3B или Qwen3.6-35B-A3B активны ~3 млрд параметров на токен, но эксперты — 90 % файла. Эксперты в RAM, внимание и роутер на GPU — и модель работает на 8 ГБ VRAM, потому что на токен читаются только выбранные эксперты. Планировщик кладёт эксперты на CPU первыми и только потом уменьшает число слоёв на GPU.

t_token = bytes_gpu / (eff_gpu × BW_gpu) + bytes_cpu / (eff_cpu × BW_cpu)   # hybrid: the CPU side dominates

Почему суммировать по тензорам

«Q4_K_M» — не тип, а смесь (часть тензоров в Q6_K), эффективно ≈ 4.8 бит/вес. Умножать параметры на «средний bpw» нельзя: один из агентов так спутал гигабайты файла с bpw (§ Fact-check, № 1). Заголовок GGUF даёт точные размеры каждого тензора, и его можно прочитать range-запросом без скачивания файла.

mmproj (кодировщик vision/audio) — отдельный файл и отдельный буфер; в --fit llama.cpp он документацией не подтверждён, runa считает его сам.

Скорость

bytes_per_token = active_weights_bytes + kv_bytes_at(ctx / 2)          # MoE: shared + n_expert_used / n_expert × expert_bytes
decode_tok_s    = eff(device, quant) × BW_bytes_s / bytes_per_token     # memory-bound ("speed of light", Kapoulkine 2024)
prefill_tok_s   = min(eff_c × FLOPS / (2 × active_params), BW-bound)    # compute-bound
ttft_s          = prompt_tokens / prefill_tok_s
eff defaults    = CUDA 0.60 · Metal 0.60 · Vulkan 0.50 · CPU 0.50   → updated per (device, quant) from measured runs

По замерам Капулкина llama.cpp достигает 58–82 % теоретической полосы RTX 4090 в зависимости от формата весов, специализированный движок — ~90 %. После каждого запуска runa записывает measured / predicted и берёт медиану — прогноз сходится к ±15 % за три запуска.

runa fit→Placement→runa run→runa bench / usage→calibration.db→eff(device, quant)↺

Plan · step by step

How to build runa and make it the best one

Полная версия с ~70 задачами и машинной проверкой каждой — в plan.md. Ниже — решения, метрики и фазы.

Decisions

IDDecision
D1Rust orchestrates; ggml (C) computes; own C/asm kernels only behind a benchmark gate: ≥ 5 % end-to-end tok/s or ≥ 2× on the isolated op, else not merged.
D2llama.cpp via llama-cpp-2 is the primary backend; mistral.rs feature-gated for models ggml cannot run; candle/burn not used for LLM inference.
D3GGUF only for local inference; refs are a path, hf:<repo>:<quant>, or a config alias.
D4Three modes = one placement planner: Placement { n_gpu_layers, tensor_overrides, kv_device, mmproj_device }; auto = planner's best plan.
D5runa-fit is a standalone library: GGUF header (local or HTTP range), hardware probe, analytic estimator with an uncertainty band, exact mode via the engine allocator when the file is local.
D6Speed = bandwidth model × eff(device, quant), calibrated from measured runs in a local SQLite DB; predictions are always ranges.
D7One ThinkConfig (Off / On / Budget / Effort); local budget forcing in our sampling loop; OpenAI reasoning.effort; Anthropic thinking: adaptive + output_config.effort; reasoning and text are separate events.
D8Media decode in Rust, encoders in C; routes native / asr / cloud; video = ≤ N frames at 1 fps with scene-change keyframes plus the audio route.
D9One Backend trait; OpenAI through async-openai (Responses API, base_url override); Anthropic through a thin reqwest + SSE client.
D10clap subcommands run / chat / fit / pull / serve / doctor / bench / models / config; figment layering; named profiles.
D11axum server, OpenAI-compatible; reasoning_content, reasoning_effort, reasoning_budget_tokens (same names as llama-server); Anthropic-compatible /v1/messages later.
D12No silent fallback: on_unfit = error | cpu | cloud:<backend>:<model>; a verdict line before the first token, always.
D13Tier 1: macOS arm64 (Metal), Linux x86_64 (CUDA, Vulkan, CPU); Tier 2: Linux aarch64, Windows x86_64.
D14Kernel candidates in order: vocab sampling, image preprocessing, audio front-end, SME2/AMX quantized mat-vec where ggml has no path.
D15Every task has a machine check; fit estimates golden-tested against llama.cpp allocator logs (±5 %); perf CI fails on > 3 % regression.
D16Pinned versions in Cargo.lock and docs/versions.md; llama.cpp upgraded monthly through the benchmark gate.

Phases

The fit checker (P1) is built before the engine (P2): it is the differentiator and needs no GPU to develop and test.

P0 — Skeleton, spikes, baselines 1 week

  • Workspace with seven crates, CI matrix (macos-14 Metal, ubuntu x86_64 CPU + CUDA build-only, windows build-only), pinned toolchain, docs/versions.md.
  • Spikes that test the risky assumptions: llama-cpp-2 with Metal/CUDA streams 64 tokens; mtmd bindings present (else bindgen over mtmd.h); an mmproj describes an image.
  • Baselines with llama-bench for Qwen3-8B Q4_K_M, gpt-oss-20b MXFP4, Qwen3-30B-A3B Q4_K_M in cpu / gpu / hybrid → docs/baselines.md. Fixtures: synthetic GGUF headers per arch, a ≤ 0.6B model, audio/video clips, recorded API responses.

P1 — Fit checker 2–3 weeks

  • GGUF reader (v2/v3, metadata, tensor table) with proptest; remote header via HTTP range with growth, HF URL resolution, header cache, sibling-quant listing. Check: runa fit hf:… < 3 s, no download.
  • Model descriptor (arch, layers, heads, head_dim, experts, sliding window, MLA, recurrent layers); exact weight bytes per ggml block type, split into dense / expert / embedding groups. Check: matches published file sizes ±0.1 %.
  • KV estimator with per-arch exceptions (±2 % of llama.cpp's KV self size); compute-buffer formula fitted on ≥ 20 logs per backend, +15 %, never underestimates.
  • Hardware probe (sysinfo, raw-cpuid, NVML, objc2-metal, ROCm SMI / Vulkan props, bandwidth table) and a bandwidth micro-benchmark stored in the device profile.
  • Placement planner (GPU bytes under VRAM − margin, experts to CPU first), speed model (decode, prefill, TTFT, hybrid), calibration DB, verdict with warnings / suggestions / exit codes / --json, exact mode via the engine allocator.

P2 — Engine and the three modes 2–3 weeks

  • Engine wrapper: load with Placement, context params, KV types, threads; verdict line before load. Streaming generation with chat templates and the sampler chain. Check: ≥ 95 % of llama-cli tg128.
  • runa run / runa chat (/think, /mode, /model), runa pull with resumable hf-hub downloads and checksums, runa models.
  • auto mode with on_unfit; MoE hybrid (ffn_.*_exps on CPU, --n-cpu-moe); KV quantization; prompt cache on disk; multi-GPU split; runa bench feeding calibration.

P3 — Thinking and cloud 2 weeks

  • ThinkConfig flags; reasoning delimiters per family (<think>, Harmony channels, Gemma tags, template kwargs); stream parser; budget forcing with grace and soft bias. Check: 100 runs on Qwen3-4B with budget 256 never exceed budget + grace; GSM8K-50 within 10 points of unlimited.
  • OpenAI adapter (Responses API, reasoning summaries, images, input_audio, base_url, field normalization); Anthropic adapter (adaptive thinking, effort, display, streaming deltas, images, PDFs, refusal, retries, cache_control). Both mock-tested with recorded fixtures plus live smoke tests behind RUNA_LIVE=1.
  • Routing anthropic: / openai:, on_unfit=cloud:…, a dated price table, keychain secrets, runa serve v1 passing the OpenAI Python SDK smoke test.

P4 — Audio and video 2–3 weeks

  • Audio decode to 16 kHz mono f32; ASR route with whisper-rs (VAD chunking, auto language) and Parakeet-TDT v3 through the official sherpa-onnx binding; native audio via mtmd mmproj; route selection auto | native | asr per backend capabilities.
  • Video via ffmpeg-sidecar: frames at 1 fps, ≤ 32 with scene-change keyframes, timestamps in the prompt, audio track through the audio route; vision via mtmd (Qwen3-VL, Gemma 3/4, InternVL, MiniCPM-V); cloud media limits with auto-downscale.
  • Fit for media: mmproj bytes, encoder buffers, tokens per frame / per second of audio in the context math; profiles of the media pipeline for P5.

P5 — Kernels and speed 2–3 weeks, time-boxed

  • Profiling harness (samply, ggml op timing), runa-kernels crate with cc build, runtime dispatch, scalar references, equivalence fuzzing, criterion benches.
  • Kernel 1 vocab sampling (AVX2/AVX-512, NEON); Kernel 2 image preprocessing; Kernel 3 (research) SME2 / AMX quantized mat-vec where ggml lacks a path. Each behind the ≥ 5 % gate, results in docs/kernels.md.
  • Speculative decoding (n-gram without a draft model, optional draft model counted by fit), native build flag vs portable builds, nightly perf CI failing on > 3 % regressions.

P6 — Server, packaging, release 2 weeks

  • Multi-model server with LRU load/unload and per-model fit checks, parallel slots, embeddings, transcriptions, Anthropic-compatible /v1/messages.
  • cargo-dist releases (mac arm64 Metal, Linux CPU+Vulkan and CUDA, Windows), Homebrew tap, docs (fit formulas, thinking, media, every config key, man page), no telemetry, localhost by default, key redaction, checksums, docs/release-1.0.md with M1–M10 measured.

P7 — After 1.0

  • mistral.rs backend behind a feature; llama.cpp RPC across machines; tool calling and JSON-schema output; NPU backends; runa fit --recommend; LoRA adapters; TUI.
